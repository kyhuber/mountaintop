# Project Context & Architecture
- Mountaintop is a browser-based implementation of the Huber brothers' trick-taking card game. One human plays an eleven-round game against one to four computer opponents, bidding on tricks and managing the high-risk Mountaintop bid. Tables are capped at five players (`MAX_PLAYERS` in `src/game.js`) because that is the largest table that renders cleanly on a phone; raise the cap only after re-measuring the layout on 360px-wide and 667px-tall viewports.
- The app is dependency-free JavaScript ES modules, semantic HTML, and CSS, served as static files. There is no build step: GitHub Pages serves the root of `main` directly at `mountaintop.kaihuber.dev`, and `index.html` loads `src/` as native modules, so merging to `main` is the deploy. The only third-party request is Google Fonts. Node's built-in test runner provides automated coverage, and GitHub Actions runs it on every push to `main` and every pull request.
- Optimization work should prioritize competitive game balance, understandable player feedback, deterministic and reproducible analysis, fast static delivery, a great experience on phones as well as desktops, and a maintainable zero-runtime-dependency architecture.

## Validated Assumptions & Optimization Log
- **2026-10-01 Tap-to-continue tricks, five-player cap, resilient saves**: Replaced the timed trick-winner pause with an explicit `trickEnd` phase that waits for a tap. This fixed two verified bugs: a human who won a trick could tap another card during the pause and push a fourth card onto a finished trick (the pause timer then wiped it), and a page reload during the pause left a completed trick on the table forever because the resume path only restarted bot turns. Saves are now validated on load under a versioned key, so a stale or malformed save falls back to the setup screen instead of a blank page. Capped tables at five players after measuring 4, 5 and 6 players in headless Chromium at 390x844, 375x667, 360x740 and 844x390: six players wrapped seats into two rows and pushed the hand below the fold on the two smaller phones, five fit everywhere. Fixed the mobile layout defects found in review: the game grid now uses `minmax(0, 1fr)` so the opponents row can no longer widen the page, seats are compact on narrow screens, the trick wraps and the trump card tucks into the felt's corner, the header fits 360px, and a short-viewport query handles landscape phones. Added `winText` so the human reads "You win the trick" instead of "You wins". Result: 27 tests pass, including a shared fake-DOM harness that drives the app through a full trick, resume, scoring and the stepper cap.
- **2026-10-01 Production scoring selected from simulation**: Human playtests are not available, so production scoring was inferred from the deterministic simulation rerun over the supported two-to-five-player range (160,000 games). Tricks-taken misses with Mountaintop at +6/-6 led every competitiveness metric at every table size: 9.62 average winner margin and 66.4% competitive finals, versus 12.37 and 56.0% for the interim symmetric +6/-6 rule and 15.72 and 46.5% for the original +10/-10 rule. Exact nonzero bids score five plus tricks, misses score the tricks taken, Mountaintop scores +6 or -6. The simulator now imports `predictionDistribution` from `src/game.js` instead of carrying its own copy, and its default player range is derived from `MIN_PLAYERS`/`MAX_PLAYERS`. See `analysis/scoring-report.md` for the full tables and the conditions under which to revisit symmetric scoring.
- **2026-10-01/a675c9a Merge repair and CI**: Two branches edited the same hunks and the auto-merge kept both sides, leaving a duplicate `leadText` declaration, a three-branch ternary in the simulator and a duplicated import in the tests. Every module failed to parse, so the suite could not run and the deployed site rendered nothing. Removed the duplicates and added a GitHub Actions workflow that runs `npm test` and `git diff --check`, so a non-parsing `main` cannot land silently again.
- **2026-10-01/3722b66 Parallel scoring simulation**: Built a deterministic worker-thread simulator crossing tricks-taken versus symmetric miss scoring with Mountaintop schedules of +10/-10, +8/-8, +6/-6 and +10/-6, with paired deals and expected-value bidding. The first run covered two to eight players; the findings held when rerun on the production range (see above).
- **2026-10-01/e727526 Centralized leader grammar**: Replaced duplicated leader-message conditionals with `leadText(player)` so the human is addressed as "You lead" while computer players use "<Name> leads."
- **2026-10-01/33cedb0 Static Pages and blind bidding**: Retained a dependency-free static deployment and implemented the one-card round as a blind bid in which each bidder's own card is excluded from its decision data. Regression coverage verifies hidden-card rendering, simultaneous bid commitment, bot independence from its own hidden card and the human bid, and unchanged visible-hand bidding in other rounds.
- **Lessons Learned**: Auto-merges that touch the same hunk from two branches can keep both sides and still look clean; run the suite on `main` in CI, never trust a merge that was not tested. Player-facing grammar must branch on the player's `human` property, every such message needs a shared formatter and a unit test, and "You wins" slipped through because the trick-winner message had neither. Hidden-information features need tests at both the game-logic and rendered-UI boundaries. Any state that is persisted on every render must be resumable from every phase, so prefer explicit phases over timers for anything the player must see. Validate saves on load and version the key whenever the shape changes. Production bots must derive choices from the active scoring function so rule changes do not leave stale thresholds, and the simulator must share that model rather than copy it. Symmetric penalties add strategic consequences but widen score gaps; lowering both Mountaintop outcomes had a far larger competitiveness effect than changing the miss rule. Measure mobile layouts with real viewports before adding features: the two defects that mattered most (page-wide horizontal overflow, trick cards covering trump) were invisible on desktop. Update this log whenever a meaningful assumption is validated, an optimization strategy changes, or new regression or performance evidence is added.

## Development & Commands
- **Dev Server**: `npm run dev` serves the repository at `http://localhost:4173` (set `PORT` to change it). There is no build command; the repository root is the deployable artifact.
- **Test Command**: `npm test` runs the complete suite with Node's built-in test runner. To run one file, use `node --test test/game.test.js`, `node --test test/blind-round.test.js`, `node --test test/app-flow.test.js` or `node --test test/simulation.test.js`. `test/helpers/app-harness.js` is a minimal fake DOM that lets tests drive `src/app.js` through bids, card plays, trick continuation and the setup stepper without a browser.
- **Manual preview**: `test/blind-preview.html` (append `?players=5`) seeds a blind-round fixture with an isolated save so the hidden-card UI can be inspected in a browser.
- **Simulation Command**: `npm run simulate:scoring -- --games=5000 --seed=20261001` runs all eight scoring variants concurrently over every supported table size and writes the reproducible results to `analysis/scoring-results.json`. Rerun it and update `analysis/scoring-report.md` whenever `scoreRound`, `predictionDistribution`, `chooseBotCard` or the player range changes.
- **Deploy**: merge to `main`. GitHub Pages serves the branch root; the custom domain is in `CNAME`.

## Code Style & System Guidelines
- Use modern JavaScript ES modules and keep browser runtime dependencies at zero unless a measured requirement justifies changing that constraint. Keep pure game rules and constants in `src/game.js`; keep browser state, rendering, persistence and event handling in `src/app.js`. Prefer small named helpers over repeated conditionals, use the player's `human` flag for human-specific behavior, and never allow hidden cards or other private state to enter a bot decision that is supposed to use public information only. Do not wrap imports in `try`/`catch` blocks.
- Game flow is a sequence of explicit phases (`predict`, `play`, `trickEnd`, `roundEnd`, `gameEnd`). Anything the player must notice waits for their input rather than a timer; timers are only used to pace bot plays, and every awaited delay checks that it has not been cancelled. Every render persists state, so every phase must be resumable on reload. Saves are validated on load; bump the `SAVE_KEY` suffix whenever the saved shape changes.
- The layout must work on phones and desktops. Check changes at 360px and 390px wide, at 667px tall, and in landscape before merging; the game grid column must stay `minmax(0, 1fr)` so no row can widen the page. Touch targets are at least 44px, hover-only effects live behind `@media (hover: hover)`, and modal panels carry `role="dialog"` with focus moved into them on render.
- Every new game-rule or formatting utility must have an accompanying unit test. Add regression tests for every corrected bug, test both human and bot paths when behavior differs, and test hidden-information behavior at both logic and UI boundaries. Run `npm test` and `git diff --check` before committing. Whenever tests validate a new assumption, an optimization is adopted or rejected, or benchmark results change, update the optimization log in this file in the same commit.
