# Project Context & Architecture
- Mountaintop is a browser-based implementation of the Huber brothers' trick-taking card game. One human plays an eleven-round game against one to seven computer opponents, bidding on tricks and managing the high-risk Mountaintop bid.
- The app uses dependency-free JavaScript ES modules, semantic HTML, and CSS. Node's built-in test runner provides automated coverage, a small Node script creates the static `dist/` output, and GitHub Pages hosts the result. Optimization work should prioritize competitive game balance, understandable player feedback, deterministic and reproducible analysis, fast static delivery, and a maintainable zero-runtime-dependency architecture.

## Validated Assumptions & Optimization Log
- **2026-10-01/3722b66 Parallel scoring simulation**: Built a deterministic worker-thread simulator and crossed current versus symmetric miss scoring with Mountaintop schedules of +10/-10, +8/-8, +6/-6, and +10/-6. We ran 5,000 full games for every two-to-eight-player condition: 280,000 games and 15.4 million player-rounds overall. Current scoring with +6/-6 produced the closest automated games (7.66-point average winner margin; 76.7% of games had at least two players within 10 points before the final round). Symmetric +6/-6 was the strongest symmetric compromise (9.67-point margin; 68.1% competitive finals), while +10/-6 generated more calls and repeat calls but retained wider score gaps. These are simulation findings, not a production scoring decision; advance the control and three leading candidates to human playtests.
- **2026-10-01/e727526 Centralized leader grammar**: Replaced duplicated leader-message conditionals with `leadText(player)` so the human is addressed as “You lead” while computer players use “<Name> leads.” We chose a shared formatter to keep all three leader-message contexts consistent. Benchmark/result: the full suite passed 12 tests in approximately 0.60 seconds, and the production build completed successfully.
- **2026-10-01/33cedb0 Static Pages and blind bidding**: Retained a dependency-free static deployment and implemented the one-card round as a blind bid in which each bidder's own card is excluded from its decision data. We chose this boundary to preserve the intended hidden-information rule while keeping GitHub Pages startup simple. Result: regression coverage verifies hidden-card rendering, simultaneous bid commitment, bot independence from its own hidden card and the human bid, and unchanged visible-hand bidding in other rounds.
- **Lessons Learned**: Player-facing grammar should depend on the player's `human` property rather than a display-name comparison, and shared wording needs unit coverage. Hidden-information features require tests at both the game-logic and rendered-UI boundaries. Paired deterministic deals and scoring-aware bids are necessary for fair rule comparisons. Symmetric penalties add strategic consequences but do not inherently create closer games; lowering both Mountaintop outcomes had a much larger competitiveness effect, while reducing only the failure penalty encouraged repeat risk without closing score gaps as much. Simulation narrows candidates but cannot measure fun, so do not change production scoring until structured human playtests validate the strategic experience. Update this log whenever a meaningful assumption is validated, an optimization strategy changes, or new regression/performance evidence is added.

## Development & Commands
- **Build Command**: `npm run build` rebuilds the production-ready static application in `dist/`.
- **Dev Server**: `npm run dev` serves the repository at `http://localhost:4173`.
- **Test Command**: `npm test` runs the complete suite with Node's built-in test runner. To run one file, use `node --test test/game.test.js` or `node --test test/blind-round.test.js`.
- **Simulation Command**: `npm run simulate:scoring -- --games=5000 --seed=20261001` runs all eight scoring variants concurrently and writes the reproducible results to `analysis/scoring-results.json`.

## Code Style & System Guidelines
- Use modern JavaScript ES modules and keep browser runtime dependencies at zero unless a measured requirement justifies changing that constraint. Keep pure game rules in `src/game.js` and browser state, rendering, persistence, and event handling in `src/app.js`. Prefer small named helpers over repeated conditionals, use the player's `human` flag for human-specific behavior, and never allow hidden cards or other private state to enter a bot decision that is supposed to use public information only. Do not wrap imports in `try`/`catch` blocks.
- Every new game-rule or formatting utility must have an accompanying unit test. Add regression tests for every corrected bug, test both human and bot paths when behavior differs, and test hidden-information behavior at both logic and UI boundaries. Run `npm test`, `npm run build`, and `git diff --check` before committing. Whenever tests validate a new assumption, an optimization is adopted or rejected, or benchmark results change, update the optimization log in this file in the same commit.
